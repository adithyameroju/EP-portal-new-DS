# The Figma → Code Loop

This is the end-to-end loop a designer runs: design in Figma → generate code
with AI → audit → review assumptions → log the build → (optionally) write the
result back to Figma. Each step below cites where its rules live.

---

<div className="flex flex-col gap-4">

<StepCard n="0" title="Step 0 — One-time setup">

{/* source: .claude/designers.md §"First-time setup" — two steps, ~2 minutes */}
Clone the repo (`git clone ... && npm install`) and open it in Claude Code.
"Claude Code automatically reads `CLAUDE.md` at the project root, which links
to all the design system rules, skills, and specs. No extra setup needed."

</StepCard>

<StepCard n="1" title="Step 1 — Design with the system in Figma">

{/* source: .claude/designers.md §"What this means for your Figma workflow" — three rules
    with their stated reasons */}
- **Use Compass components, not custom frames.** "If you use a Compass Button,
  the generator produces a correct `<Button variant="default">`. If you draw a
  custom rectangle ... it may also guess wrong."
- **Use the Compass color styles, not local colors.** "The code generator is
  trained to refuse hardcoded hex values" — unmapped local colors get flagged
  and questioned, never silently substituted.
- **Use the spacing scale.** "The generator rounds to the nearest step and
  flags the rounding in its assumptions list."

{/* source: RESOLVED — .claude/specs/foundations/spacing.md:5 is the source of allowed values
    ("If a spacing value isn't listed here, it doesn't exist in the system"); designers.md's
    11-value 8-point grid is the everyday subset, not a competing system. */}
**Which spacing list governs?** The spacing foundation spec is authoritative —
it is the source of allowed values: "If a spacing value isn't listed here, it
doesn't exist in the system" (`spacing.md`). The Designer Guide's 11 named
8-point values (4–96px) are **the everyday subset** designers reach for most,
**not a competing system**. A value outside that subset is still valid if it's
on the full scale; the generator rounds to the nearest scale step and flags the
rounding in its assumptions list.

</StepCard>

<StepCard n="2" title="Step 2 — Frame it and copy the link">

{/* source: .claude/designers.md §"How to hand off a frame" steps 1–2 */}
"The Figma frame should contain exactly the component or screen you want
generated — no extra artboards, no helper notes on top of the design." Then
right-click → "Copy link to selection."

</StepCard>

<StepCard n="3" title="Step 3 — Hand it to the AI">

{/* source: .claude/designers.md §"How to hand off a frame" step 3; README.md
    §"AI-assisted code generation"; CLAUDE.md linked-documentation table (generate-code.md
    must be read before generating UI code) */}
Give the link to Claude Code or Cursor (with Figma MCP) with the instruction:
"Generate code for this frame using Compass." The tool works under
`.claude/skills/generate-code.md`, which it must read before generating any UI
code from a Figma frame.

</StepCard>

<StepCard n="4" title="Step 4 — The AI runs the 5-step generate-code process">

{/* source: .claude/skills/generate-code.md Steps 1–5, plus "Before you start" */}
What the skill obliges the AI to do — useful to know so you can tell when it's
being skipped:

1. **Analyze the frame** — identify every component, layout, spacing, colors,
   text styles, states — and "output a brief analysis before writing code."
2. **Map to Compass components** — every element maps to an existing
   `components/ui/` component; if something doesn't map, the AI must **stop
   and ask** before creating anything new.
3. **Write the code** — imports only from `@/components/ui/`, icons only from
   `lucide-react`, semantic tokens only, spacing from the scale, mobile-first
   responsive classes.
4. **Self-audit** — a 11-point checklist (no hex, no arbitrary values, no
   reimplemented components, composites used "at every level," correct APIs).
   "If any check fails, fix it before presenting."
5. **Present with two sections** — "What I did (confident)" and "What I
   assumed (please confirm)." More on reading that list in
   *Working with AI*.

</StepCard>

<StepCard n="5" title="Step 5 — Run the token audit (the hard gate)">

{/* source: CLAUDE.md §Audit command ("zero errors required before committing") */}

<CommandLine
  line="npm run audit                 # token audit — hard gate, zero errors required"
  command="npm run audit"
/>

`npm run audit` catches hardcoded hex, arbitrary pixel values, and raw
Tailwind color utilities — "zero errors required before committing. If audit
fails, fix before proceeding."

</StepCard>

<StepCard n="6" title='Step 6 — Review "What I assumed"'>

{/* source: .claude/designers.md §"How to hand off a frame" step 4 — quoted */}
"Review the assumptions list. Trivial items (spacing rounded from 14px →
12px, placeholder text) need no reply. Structural decisions (a component it
wasn't sure about, a color it couldn't map) need a quick 'yes' or 'use X
instead.'"

</StepCard>

<StepCard n="7" title="Step 7 — Log the build, then score it">

{/* source: drift-log/README.md §"How an entry gets here" — quoted/condensed;
    .claude/skills/compass-audit/SKILL.md §"Score a build" (the log → score → dashboard
    sequence, verbatim) + hard rule 4 (token-audit stays the commit gate; compliance
    audit is advisory) + §Cadence ("Capture: every build") */}

<div className="flex flex-col gap-1">
  <CommandLine
    line='npm run log            # capture: paste "What I assumed", files auto-detected'
    command="npm run log"
  />
  <CommandLine
    line="npm run audit:compliance -- --entry drift-log/entries/<entry>.json"
    command="npm run audit:compliance -- --entry drift-log/entries/<entry>.json"
  />
  <CommandLine
    line="npm run dashboard      # regenerate drift-log/dashboard.html"
    command="npm run dashboard"
  />
</div>

`npm run log` "asks you to paste the 'What I assumed' block from the AI's
output," auto-detects the files the session changed and the Compass components
they import, and writes one JSON entry to `drift-log/entries/`. It is
"designed for zero friction — if any auto-detection fails it degrades
gracefully." Capture happens **every build**.

The compliance audit then scores that entry's files against the C1–C7 rubric
(tokens, provenance, composites, spec coverage, naming, imports) and writes a
report. Unlike Step 5, this score is advisory: "token-audit stays the commit
gate ... the compliance audit is advisory." The weekly/monthly drift detection
and the tightening proposals only read this ledger.

</StepCard>

<StepCard n="8" title="Step 8 — (Optional) Write the result back to Figma">

{/* source: .claude/skills/write-to-figma.md — critical rule, Step 1, and Fallback;
    CLAUDE.md Component rules ("Figma write-back: library instances only") */}
When you want the built screen represented in Figma, the write-to-figma skill
applies. Its critical rule: "**NEVER** use `figma.createFrame()` or
`figma.createRectangle()` to represent a Compass component. Always use
`figma.importComponentByKeyAsync(key)`" with keys from
`.claude/specs/figma/component-keys.md`. Raw frames are acceptable only for
page containers, layout rows/columns, and spacers. If a component's key is
missing from the registry, the skill must flag it ("Warning: [Component]
written as raw frame — key not in registry"), never hide it.

</StepCard>

<StepCard title="What happens after — the loop closes">

{/* source: .claude/skills/compass-audit/SKILL.md §Detect, §Prescribe, §Cadence, hard rule 1 */}
On a weekly-to-monthly cadence, `npm run detect` reads the last N ledger
entries and clusters drift hotspots; `npm run prescribe` scaffolds a
tightening-plan **proposal** in `drift-log/proposals/`. "The loop proposes,
the owner approves" — no spec or rule is ever edited automatically. Your
logged assumptions are the raw material: "a repeated assumption = a spec that
failed to decide something."

</StepCard>

</div>

## Open questions in this loop

{/* source: RESOLVED — .claude/contributing.md:82-84 — components/blocks/ is "where Acko-specific
    screen compositions live — things like login forms, dashboard cards ... assembled from
    components/ui/ primitives and ... less strictly gated"; full-screen builds go to an app/ route. */}
**Where do designer-generated screens live?** Both — by build type. A reusable
composition goes in `components/blocks/`, "where Acko-specific screen
compositions live — things like login forms, dashboard cards ... assembled from
`components/ui/` primitives and ... less strictly gated" (`contributing.md`). A
full-screen build goes to an `app/` route instead.

{/* source: RESOLVED — designers commit their reviewed build to components/blocks/ (the
    "less strictly gated" area, contributing.md:82-84); developers pick it up from there. */}
**Who commits the build?** The designer commits their own reviewed build to
`components/blocks/` (the "less strictly gated" area); developers pick it up
from there. Handing the composition off through the repo — rather than
person-to-person — closes the loop, and keeps the CODEOWNERS-gated
`components/ui/` primitives out of the designer's path.

{/* source: RESOLVED — the meta-driven surface (Storybook status badges generated from each
    component's meta.ts) is the authoritative live status. The designers.md table was refreshed
    2026-07-07 to 55 components / 33 specs / 10 Code Connect, so the old "only Button/Input/Card"
    wording no longer applies. */}
**Which surface is the truth for component status?** The **meta-driven
surface** — the Storybook status badges generated from each component's
`meta.ts` — is the authoritative live status of which components have specs and
Code Connect. It cannot drift from the code, because Storybook, the compliance
audit, and the scaffold pipeline all read that same `meta.ts` contract. Point
designers at the badges rather than at any hand-maintained table.
